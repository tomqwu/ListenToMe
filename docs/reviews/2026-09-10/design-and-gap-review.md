# ListenToMe production review

**Decision draft · September 10, 2026 · source 3c542e3 · candidate 1.3.0/build 6**

**Recommendation: do not promote the existing 1.3.0 DMG as a broadly validated production release.** Aim today for a focused release to existing users/pilot users after the blocking gates below pass. Keep speaker identification opt-in beta. A signed installer, 215 passing Core tests, and 97.24% Core coverage are useful foundations; they do not establish capture reliability, durable saving, accurate speaker attribution, or a usable first-run experience.

Scope reviewed: product strategy, source architecture, UI/layout, onboarding, audio and transcription, speaker identity, AI behavior, history/export, privacy controls, CI, and distribution. This inventory covers the gaps found in that scope; it is not a guarantee that no other defects exist. [Evidence and reproductions](evidence.md) distinguish verified defects, source findings, and outstanding runtime validation. [Today's execution plan](production-roadmap.md) assigns gates and sequence.

## Product direction

The strongest promise is: **“Keep a reliable record of the meeting, understand what was decided, and get useful help while you participate—with clear control over where your data goes.”**

Retain native macOS, on-device transcription, explicit choice of local or cloud AI, and a useful default workflow without a subscription to ListenToMe. Treat Ollama model setup as a supported dependency that onboarding must diagnose. Three independent AI models and 18 presets are power-user capabilities; they should not dominate the first meeting.

Prioritize individual Mac users already using Ollama. Validate the capture → save → review → export loop before expanding providers, integrations, semantic search, automatic meeting detection, or team workspaces. “Free app” should be distinct from possible external model-provider charges. Keep administrative privacy/recording guidance practical; do not claim enterprise compliance certification.

Today’s reliable core should be live two-source transcription, visible capture/model health, durable session saving/recovery, usable session history, clear local/cloud routing, and summaries that retain earlier decisions. Speaker identification and multilingual code-switching need a published beta boundary until real recordings establish quality. Native capture should remain useful when AI is unavailable.

## What to retain

- SwiftUI/AppKit native app and reusable theme/components; horizontal and vertical split views already exist.
- Core separated from macOS adapters, injectable capture/transcription/LLM protocols, and extensive Core tests.
- Independent AI roles, streaming and cancellation generation guards, configurable reference budgets.
- Explicit opt-in speaker processing, names propagated into transcript text, and conservative identity matching for ambiguous re-clustering.
- Source labels, guarded capture-buffer generations, teardown draining, local session storage with atomic writes, Keychain secrets, bounded file ingestion with folder symlinks excluded.
- Developer/release bundle-ID separation and an established Developer ID/notarized universal-DMG pipeline.

## GUI and layout assessment

The current command-center implementation is powerful but crowded. A permanent rail contains engine/language, a proactive toggle, preset, three models, and token/turn counters; the center holds the transcript and context; three independently scrolling AI panes share the right column. Useful meeting state—whether both sources are actually arriving, whether the session is saved, what is still finalizing—has less prominence than setup detail.

The main view requires at least 1,100 × 560 points. Settings is a fixed-width 440-point VStack without a ScrollView, despite a long stack of labels, controls, and help text. Small-window fit and sheet height are risks requiring a fresh native test. Informational text uses 10–12.5-point sizes. Calculated tertiary-text contrast is 2.61:1 in light mode and 3.31–3.54:1 in dark mode, below the [4.5:1 normal-text benchmark](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**Today’s UI changes:** large icon-plus-text **Save conversation** and **New conversation** actions, with safe save-before-reset behavior; a fixed, visible session-status area; explicit mic/system health and AI destination; “Saving / Saved / Save failed”; “Finalizing” after Stop; scrollable Settings with anchored Save/Cancel; readable informational colors; honest shortcut labels; explicit empty/error states. Preserve the split-view structure to limit regression risk.

**Next layout iteration:** collapsible setup sidebar; transcript as the dominant left region; right side with Live summary / Ask / Deep tabs, with power users able to restore all panes. Use a labeled primary Start/Stop action; a short “More” menu for infrequent actions; keep the current model/destination visible per AI role. History must open a session detail view, not just display snippets. Add an obvious New session command distinct from pause/resume.

[Proposed layout wireframe](proposed-layout.svg) is a design proposal with synthetic content, not a screenshot or implemented behavior. Do not attempt the full layout replacement during today’s stabilization window.

## Architecture direction

Move lifecycle, persistence and speaker scheduling out of SwiftUI view state into a tested session coordinator. Use a versioned session model with ID, source/run timeline, segments, per-source partials, speaker assignments/names, notes/references, AI outputs, and processing/save status. Keep capture-source health and AI readiness independent.

Write the raw finalized transcript durably before enrichment. Speaker analysis and AI attach revisions to that record; they cannot block saving or silently replace completed user-visible work. Preserve the existing generation-token approach, but test it across Stop/Start, language changes, model changes, imports, window close and failed persistence. Use an explicit state machine: Ready → Starting → Recording → Finalizing → Saved, with recoverable/degraded errors rather than several unrelated booleans.

Use one model policy boundary for discovery, default selection, request routing and privacy display. Distinguish model availability, process location, authentication and user consent. A running Ollama server is not proof that a selected model is ready or local.

## Release judgment

Today is achievable only as a conditional, constrained target. Close G01–G10 or make a clearly documented scope reduction that removes an affected feature while preserving the capture/save/review promise. Do not use “experimental” to excuse data loss, misleading cloud routing, or hidden base-path failure. Complete the bounded UI truthfulness fixes and the real-device acceptance matrix before publication.

If the hardening work or evidence cannot finish today, publish a clearly labeled prerelease to the pilot audience, or hold distribution. Broad public promotion and production-grade speaker-identification claims should wait for measured evidence. Yesterday's 1.3.0 DMG remains a packaged development candidate until these gates pass.
